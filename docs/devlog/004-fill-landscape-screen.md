# 004. 폰 가로 화면을 끝까지 채우기 (노치 옆 여백 없애기)

- 날짜: 2026-10-05
- 분류: 개선
- 계기
  - 사용자가 아이폰 홈 화면 웹 앱([003](003-iphone-home-screen-app.md))을 가로로 돌려 플레이했다.
  - "옆 화면 여백이 너무 신경 쓰인다. 폰 화면 비율에 맞춰 여백 없이 자연스럽게 맞춰 달라"고 요청했다.
- 관련 커밋: (커밋 후 채움)

## 1. 배경

원인은 두 가지였다.

1. **아이폰이 노치 양옆을 비워 둔다.**
   - 노치·다이내믹 아일랜드가 있는 아이폰은 가로 화면에서 웹 페이지를 **안전 영역** 안에만 그린다.
   - 안전 영역: 노치·다이내믹 아일랜드·둥근 모서리·홈 바에 가리지 않는 부분.
   - 웹 페이지가 따로 설정하지 않으면(`viewport-fit` 기본값 `auto`) iOS가 양옆을 비우고 페이지 배경색으로 칠한다([WebKit 블로그](https://webkit.org/blog/7929/designing-websites-for-iphone-x/)).
   - 다이내믹 아일랜드 기종은 가로일 때 좌우가 약 59pt씩이다. 852pt 폭 중 약 14%가 빈 띠가 된다.
2. **로그인 배경 그림이 화면보다 짧다.**
   - 배경을 `background-size: contain`으로 그렸다. 그림 전체가 항상 보이게 하려는 설정이었다.
   - 그림은 16:9인데 요즘 폰은 가로로 더 길다(약 19.5:9). 그래서 그림 양옆에 하늘색·연두색 띠가 한 번 더 생겼다.

## 2. 검토한 선택지와 결정

### 2-1. 화면 전체

| 선택지 | 장점 | 단점 |
|---|---|---|
| 그대로 두기 | 할 일 없음 | 양옆 빈 띠가 계속 보인다 |
| `viewport-fit=cover`만 켜기 | 한 줄 수정 | 화면 가장자리 버튼이 노치·둥근 모서리·홈 바 밑에 깔린다. 수정 전 코드로 확인해 보니 버튼·입력칸이 노치·홈 바와 겹치는 곳이 **34건** 나왔다(4장) |
| **`viewport-fit=cover` + 버튼만 안전 영역 안으로** ✅ | 배경은 끝까지 차고, 버튼은 가리지 않는다. 노치 없는 화면에서는 안전 영역이 0이라 그대로다 | 가장자리 UI를 하나씩 찾아 고쳐야 한다 |

**결정: 배경은 화면 끝까지 그리고, 눌러야 하는 UI만 안전 영역만큼 안쪽에 둔다.**
- 노치가 없는 폰, 태블릿, 데스크톱은 안전 영역 값이 0이다. 그래서 버튼 위치가 바뀌지 않는다.
- [CLAUDE.md](../../CLAUDE.md)의 "웹 동작(브라우저 탭)을 바꾸지 않는다" 원칙도 지킬 수 있다.

### 2-2. 로그인 배경

| 선택지 | 폰 가로(그림보다 가로로 긴 화면) | 태블릿·세로(그림보다 세로로 긴 화면) |
|---|---|---|
| `contain` (기존) | 양옆에 띠 | 그림 전체, 위아래에 띠 |
| `cover` | 꽉 참. 위아래 조금 잘림 | 꽉 참. 대신 그림 좌우가 크게 잘려 왼쪽 알 캐릭터가 사라질 수 있다 |
| **폭에 맞추기 `100% auto`** ✅ | `cover`와 같다. 꽉 차고 위아래만 조금 잘림 | `contain`과 같다. 그림 전체, 위아래에 띠 |

**결정: 폭에 맞추기.**
- 양옆 띠는 어떤 화면에서도 생기지 않는다.
- 그림 좌우 끝(알 캐릭터, 사슴벌레)은 어떤 화면에서도 잘리지 않는다.
- 잘리는 곳은 폰 가로에서 그림 위아래의 나뭇잎·풀밭 가장자리뿐이다.
- 노치와 상관없이 적용된다. 데스크톱도 창이 16:9보다 가로로 길면(예: 1920×969) 양옆 띠 대신 화면을 꽉 채운다. 카드 위치·크기는 그대로다(4장).

## 3. 구현

### 3-1. 화면 끝까지 그리기

- **`index.html`**: viewport에 `viewport-fit=cover`를 넣었다.
- **`src/index.css`**: `:root`에 안전 영역 변수 4개를 만들었다.
  - `--safe-top`, `--safe-right`, `--safe-bottom`, `--safe-left`
  - 값: `var(--safe-area-inset-top, env(safe-area-inset-top, 0px))`
  - 아이폰은 브라우저가 주는 `env(safe-area-inset-*)`를 쓴다.
  - 안드로이드 앱은 Capacitor가 `<html>`에 넣어 주는 `--safe-area-inset-*`를 먼저 쓴다.
    - Capacitor 8.5.2 소스(`SystemBars.java`)에서 동작을 확인했다.
    - `viewport-fit=cover`이고 WebView가 140 이상이면 앱 화면을 상태 바·내비게이션 바 뒤까지 넓힌다. 그리고 정확한 안전 영역 값을 이 변수로 넣어 준다.
    - 그보다 오래된 WebView는 `env()` 값이 틀릴 수 있어서, Capacitor 변수를 먼저 쓴다.

### 3-2. 가장자리 UI를 안전 영역 안으로

원칙은 **"원래 간격 + 안전 영역"** 이다.
- 예) 목장 프로필 카드: 화면 끝에서 12px → 노치 안쪽 경계에서 12px(화면 끝에서 71px)

| 종류 | 방법 | 대상 |
|---|---|---|
| 화면 위에 띄운 UI(`absolute`, `fixed`) | 원래 위치값은 그대로 두고 `margin`을 안전 영역만큼 더 준다 | 목장·친구 목장의 프로필·알림·설정, 편집·방명록, 날씨, 탐험도우미, 아래 메뉴, 편집 완료, 인테리어 꺼내기, 돌아가기, 로그인·뒤로가기 안내 메시지 |
| 일반 배치 UI | `padding`을 `calc(원래 값 + 안전 영역)`으로 | 세부 화면(도감·미션 등) 헤더·본문, 서식지 화면 버튼 줄·정보 패널, 프로필 저장 바 |

- 화면 위에 띄운 UI에 `margin`을 쓴 이유
  - `index.css`에는 같은 클래스 규칙(`.ranch-side-hud`, `.ranch-egg-help` 등)이 화면 크기별로 여러 번 반복돼 있다.
  - 위치값을 바꾸려면 반복된 규칙을 모두 찾아 고쳐야 한다.
  - `absolute` 요소는 `margin`만큼 더 안쪽으로 들어간다. 그래서 파일 끝에 규칙 하나만 추가하면 된다.
- 목장 지도, 서식지 사진, 세부 화면 배경은 손대지 않았다. 원래 화면 전체를 덮게 되어 있어서 그대로 끝까지 찬다.

### 3-3. 로그인 화면

- 배경을 `background-size: 100% auto`로 바꿨다(2-2의 결정).
- 로그인 카드 크기 계산(`computeScale`, `src/pages/auth/authVisuals.jsx`)도 같은 기준으로 바꿨다.
  - 보이는 그림 영역 = 화면 폭 × (화면 높이와 폭에 맞춘 그림 높이 중 작은 값)
  - 여기서 안전 영역을 뺀 크기 안에 카드가 들어가게 한다.
- 안전 영역 값은 JS에서 숫자로 바로 읽을 수 없다(`env()`가 섞인 CSS 변수라서).
  - 그래서 보이지 않는 요소에 `padding`으로 걸고, 계산된 값을 읽는다(`readSafeArea`).
- 화면 전체에 안전 영역만큼 `padding`을 줬다. 카드는 안전 영역 가운데에 오고, 배경은 `padding`까지 포함한 화면 전체에 그려진다.

## 4. 검증

Playwright(Chromium 141)로 실제 빌드를 띄워 확인했다.
- 아이폰 안전 영역: Chrome DevTools Protocol `Emulation.setSafeAreaInsetsOverride`로 흉내 냈다.
  - 다이내믹 아일랜드 기종(아이폰 15·16) 가로: 852×393, 좌우 59, 아래 21
- 수정 전 화면: iOS가 양옆을 비우는 모습을 흉내 내려고, 가운데 734px만 웹 화면으로 찍었다(1장 이미지 왼쪽).
- 홈 화면 앱 모드(`navigator.standalone = true`)로 열었다. 서버 응답은 빈 진행도로 대체했다.

"노치·홈 바 점검"은 이렇게 했다.
- 버튼·링크·입력칸마다 노치(좌우)·홈 바(아래) 영역과 겹치는지 본다.
- 겹치면 그 부분을 여러 점 찍어서, 실제로 그 요소가 눌리는지(다른 것에 가려지거나 잘리지 않았는지) 확인한다.
- 스크롤되는 페이지는 맨 아래까지 내린 뒤 홈 바 영역을 본다. 스크롤해서 올릴 수 있는 내용은 문제가 아니기 때문이다.
- 목장 지도 속 서식지(지도 세계의 일부)는 뺐다(5장).

| 항목 | 결과 |
|---|---|
| 노치·홈 바 점검 (아이폰 15·16 크기, 19가지 화면·상태) | **0건**. 같은 점검을 수정 전 코드에 `viewport-fit=cover`만 켠 상태로 돌리면 **34건**(버튼·영역 겹침 기준. 목장 12, 친구 목장 4, 도감·미션·AI 말벗·프로필 등) |
| 기종별 점검 (13 mini 812×375, 14·16e 844×390, 15·16 852×393, 16 Pro Max 956×440) | 4개 기종 모두 0건. 로그인·회원가입 카드도 모두 안전 영역 안 |
| 긴 페이지 좌우 점검 (도감·미션·가방 등 10개 화면, 스크롤 전체) | 좌우 노치 영역에 걸친 버튼 0건 |
| 시작 흐름 (첫 주소 `/`부터) | 세로로 열기 → 로그인 화면 + 가로 안내 → 가로로 돌림 → 안내가 사라지고 로그인 카드가 안전 영역에 맞게 다시 계산됨 → 로그인 → 목장. 오류 없음 |
| 목장 위치 (852×393) | 프로필 카드 왼쪽 71px(59+12), 알림·설정 오른쪽 끝 781px(852−59−12), 아래 메뉴 아래쪽 365px(홈 바 영역이 시작되는 372px보다 위) |
| 안드로이드 앱 흉내 | Capacitor처럼 `<html>`에 위 24px·오른쪽 48px 값을 넣었다. 프로필 카드 위쪽이 12→36px, 알림·설정 오른쪽 끝이 788→740px로 바뀜 |
| 노치 없는 화면 회귀 (데스크톱 1440×900, 태블릿 1180×820, SE 가로 667×375, 폰 세로 390×844 × 8개 화면 = 32건) | 버튼·입력칸·헤더 위치가 32건 모두 수정 전과 같음. 화면이 실제로 달라진 곳은 SE 로그인·회원가입 배경뿐이다(SE 화면이 그림보다 0.1% 넓어서 폭 맞춤이 적용됨). 그 밖의 1~3픽셀 차이는 같은 빌드를 두 번 찍어도 생기는 렌더링 차이였다 |
| 데스크톱 넓은 창 로그인 (1920×969) | 배경이 화면을 꽉 채움(수정 전에는 양옆에 띠). 로그인 카드 위치·크기는 수정 전과 같음 |
| 린트·빌드 | 바꾼 `.jsx` 10개를 ESLint로 직접 검사: 새 오류 0건(`RanchHabitat.jsx`의 기존 오류 2건은 수정 전과 같음). `vite build` 통과. Tailwind가 만든 CSS에서 `calc(1rem + var(--safe-left))` 같은 값이 그대로 나오는 것도 확인 |

## 5. 한계와 남은 일

- [ ] **실제 아이폰 확인**: Safari(WebKit)가 아니라 Chromium의 안전 영역 흉내로 확인했다. 실기기에서 아래를 확인해야 한다.
  - 노치 양옆 빈 띠가 사라졌는지
  - 버튼이 노치·홈 바에 가리지 않는지
  - 로그인 카드 위치
- [ ] **배포 후 적용**: main에 합쳐져 Vercel에 배포돼야 홈 화면 앱에 반영된다.
  - 이 앱은 서비스 워커가 없어서 옛 화면을 따로 저장해 두지 않는다. 배포 뒤 홈 화면 앱을 완전히 닫았다가(앱 전환 화면에서 위로 밀기) 다시 열면 새 버전을 불러온다.
- [ ] **안드로이드 실기기**: 이 변경으로 WebView 140 이상인 폰에서는 앱 화면이 상태 바·내비게이션 바 뒤까지 넓어진다.
  - 흉내로만 확인했다. 실기기에서 상단 UI가 상태 바에 가리지 않는지 확인해야 한다.
  - [001](001-web-to-android-app.md)의 "상태바·내비게이션 바" 항목 중 안전 영역 정리는 이번에 했다. 바를 숨기는 전체화면은 남았다.
- [ ] **로그인 배경 위아래**: 폰 가로에서는 그림 위아래가 약 9%씩 잘린다(나뭇잎·풀밭 가장자리). 캐릭터는 모두 보인다.
  - 태블릿처럼 그림보다 세로로 긴 화면은 예전처럼 위아래에 하늘·풀밭 그라디언트 띠가 보인다. 그림 좌우를 자르지 않으려고 그대로 뒀다.
- [ ] **목장 지도 속 서식지**: 서식지 그림은 지도의 일부라 화면 끝 노치 밑까지 걸칠 수 있다. 대부분은 안전 영역 안에 있어서 누를 수 있고, 지도를 끌어 옮길 수도 있다.
- [ ] **린트 범위 (작업 중 발견)**: `npm run lint`(`eslint .`, ESLint 8)는 `.jsx`를 검사하지 않는다.
  - `--ext .js,.jsx`로 돌리면 기존 react-hooks 오류(effect 안에서 바로 setState)가 약 12건 나온다.
  - 이번 작업과 별개로 정리한다.

## 6. 포트폴리오 포인트

- "여백이 신경 쓰인다"는 피드백의 원인을 **두 가지**(iOS 안전 영역의 기본 동작, 로그인 배경의 `contain`)로 나눠 찾았다.
- 화면을 늘리기만 하지 않고 **"배경은 끝까지, 버튼은 안전 영역 안"** 이라는 원칙을 세웠다.
  - 왜 필요한지는 숫자로 보였다. 늘리기만 하면 버튼·입력칸이 노치·홈 바와 겹치는 곳이 34건 생긴다.
- 반복된 CSS 규칙을 고치지 않고 `margin`을 더하는 방식으로 변경 범위를 줄였다.
  - 노치 없는 화면 32건이 그대로인 것을 자동 비교로 확인했다.
- 아이폰과 안드로이드 앱을 **CSS 변수 하나**로 함께 처리했다. 안드로이드 쪽 동작은 Capacitor 소스를 읽어서 확인했다.
