## 1. 배경

"게임답지 않다"는 느낌이 어디서 오는지 먼저 쟀다.
- 측정 환경: Playwright(Chromium 141), 폰 가로 852×393, 홈 화면 앱 모드.
- 회선: 측정용 HTTP/2 프록시로 두 가지를 흉내 냈다. 느린 회선(1.6Mbps, 지연 150ms)과 보통 회선(10Mbps, 지연 40ms).

로그인된 상태로 앱을 처음 열었을 때 보인 순서는 이랬다.

> 흰 화면 → 아이보리 바탕의 "불러오는 중" 스피너 → 아이보리 바탕의 목장 뼈대 → 배경이 위에서부터 줄 단위로 그려짐 → 대객체(숲·연못 등)가 하나씩 툭 나타남

연출이 없는 것보다 **화면이 조립되는 과정이 그대로 보이는 것**이 더 컸다. 원인은 세 가지였다.

| 원인 | 실측 |
|---|---|
| 효과음·배경음 mp3 67건이 앱을 열자마자 목장 그림과 회선을 다툼 | 느린 회선에서 목장 배경 준비 39.2초. mp3만 막으면 12.9초 |
| 화면 JS(라우트 청크)를 미리 받지 않음 | 처음 가는 화면마다 헤더까지 지워지고 스피너가 54~278ms 보임 |
| 큰 PNG 그림 | 서식지 배경 1.1~1.4MB, 목장 연못 대객체 2.9MB, 도감 첫 방문 때 곤충 그림이 회선을 독점(도감 배경 51.9초) |

그래서 **원인을 먼저 없애고(1단계), 그 위에 연출을 얹는(2단계)** 순서로 정했다. 연출부터 얹으면 조립 과정 위에 애니메이션만 하나 더 보이게 된다.

## 2. 검토한 선택지와 결정

연출 방식은 설계안 3개를 만들고, 두 기준으로 따로 심사해 골랐다.
- 설계안: ① 페이지 바깥 커튼 하나로 모든 이동을 잇는 안 ② 목장(지도)에서 서식지(장소)로 카메라가 들어가는 안 ③ 끊김 원인을 먼저 없애고 투명도만 쓰는 안전한 연출을 얹는 안
- 심사 기준: 가로 폰으로 노는 초등 저학년 아이가 느끼는 부드러움, 그리고 엔지니어링 위험(튜토리얼 겹침 순서, fixed 팝업, 뒤로가기 처리)
- 심사 결과를 합쳐 ③을 바탕으로 ①의 커튼을 장소 전환에만 가져왔다. 아래 표는 그 과정에서 비교한 방식들이다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| 모든 화면 이동을 커튼으로 덮기 | 어디서나 같은 게임 느낌 | 목장↔도감처럼 자주 오가는 이동마다 약 340~700ms가 늘고, 덮는 동안 입력이 막혀 아이가 답답하다 |
| 목장 카메라가 서식지로 날아 들어가는 줌(flyTo) | 공간이 이어지는 느낌이 가장 강하다 | 돌아올 때 카메라 위치를 정확히 되돌려야 한다. 카메라 조상에 transform이 남으면 튜토리얼 타깃(z-110)과 fixed 팝업의 기준이 바뀐다 |
| 브라우저 View Transitions API | 브라우저가 스냅샷으로 전환을 그려 준다 | "다음 장면 그림이 준비될 때까지 덮어 두기"를 직접 제어하기 어렵다. 지원하지 않는 기기를 따로 처리해야 한다 |
| 라우트 전체를 framer-motion으로 페이드·슬라이드 | 구현이 간단하다 | 페이지 조상에 transform·opacity가 남아 튜토리얼 타깃이 갇히고, 나가는 화면과 들어오는 화면이 동시에 마운트된다 |
| **장소 전환에만 원형 커튼 + 나머지는 지연 없는 도착 페이드 + 로딩 장면 하나로 통일** ✅ | 목장↔서식지라는 "장소 이동"에만 상징 연출을 쓰고, 자주 오가는 화면은 이동을 늦추지 않는다 | 화면마다 연출이 다르다. 대신 규칙(장소=원, 메뉴=페이드)이 단순해서 아이도 구분하기 쉽다 |

**결정: 마지막 안.**
- 원형 커튼: 탭한 서식지 자리에서 그 서식지 색의 원이 퍼져 화면을 덮는다. 돌아올 때는 원이 방금 떠난 서식지 자리로 접혀 들어가며 지도가 드러난다.
- 안전 규칙 하나를 끝까지 지킨다. **페이지 콘텐츠의 조상에는 transform, opacity<1, filter, will-change, isolation을 새로 남기지 않는다.**
  - 이유: 이런 값이 남으면 튜토리얼 타깃(z-110)이 그 안에 갇혀 덮개 아래로 숨고, fixed 팝업의 기준이 화면이 아니라 그 조상으로 바뀐다.
  - 그래서 커튼은 body에 붙는 별도 레이어(portal)로 그리고, 원 div 하나의 `transform: scale`만 움직인다.
- 브라우저 탭에도 같은 연출을 적용했다. "게임다운 흐름"은 제품의 동작이라서다.
  - 예외: 브라우저 탭에서 뒤로가기(POP)로 목장에 올 때는 커튼을 쓰지 않는다. Safari 스와이프 뒤로가기의 자체 전환과 겹치기 때문이다. 앱과 홈 화면 앱에서는 이때도 커튼이 접혀 들어간다.
- 끄는 스위치를 둔다. `src/utils/motion.js`의 `SCENE_TRANSITIONS_ENABLED = false`면 원형 커튼과 도착 페이드가 꺼지고 원래의 즉시 이동으로 돌아간다.
- html·body 배경은 이번에도 칠하지 않았다. 칠하면 아이폰 가로 화면의 노치·안전 영역 색이 바뀐다([004](004-fill-landscape-screen.md)·[005](005-ios-rotation-shift.md)). 로딩 장면도 `position: fixed` 레이어로만 그린다.

## 3. 구현

### 3-1. 1단계: 조립 과정이 보이지 않게 (`e7fa096`)

- **소리는 첫 장면 뒤로** — `src/utils/sceneReady.js`, `sound.js`, `SoundAssetPreloader.jsx`, `BackgroundMusicController.jsx`
  - 첫 장면이 다 그려지면 `markSceneReady()`가 신호를 한 번 보낸다. 효과음 미리받기는 이 신호와 유휴 시간을 기다린 뒤 3개씩 나눠 받는다.
  - 효과음마다 audio를 3개씩 미리 만들던 것을 1개로 줄이고, 연타로 더 필요할 때 채운다(같은 파일이라 HTTP 캐시를 쓴다). 그 결과 첫 내용 전에 시작하는 mp3 요청이 67건에서 0~1건이 됐다(4-2 표).
  - 배경음은 장면 준비 신호나 첫 터치 중 먼저 오는 쪽에서 시작한다. 터치에서 시작하는 경우는 같은 핸들러 안에서 재생해 iOS 자동재생 제한을 지킨다.
- **화면 JS 미리받기** — `src/utils/lazyWithPreload.js`, `src/router/routeChunks.js`
  - `React.lazy`는 모듈을 미리 받아 둬도 처음 렌더할 때 한 번은 대기 화면을 그린다. 그래서 다 받은 모듈은 lazy를 거치지 않고 바로 렌더하는 래퍼를 만들었다.
  - 목장이 다 그려지고 1.5초 뒤 유휴 시간에 10개 화면의 JS를 받는다. 버튼을 누르는 순간(pointerdown)에도 받는다.
  - 로그인·회원가입 화면은 첫 화면이라 앱 본체에 함께 묶었다.
- **그림 줄이기** — `scripts/convert-scene-images.mjs`
  - 큰 그림 17장을 WebP로 바꿨다. **15.10MB → 2.67MB(18%)**.
  - 연못 대객체(2.9MB)는 화면에 그려지는 크기(가로 900px)로 줄여 180KB가 됐다.
  - 도감 곤충 카드 그림은 화면에 들어올 때만 받는다. 대객체 그림에는 크기를 미리 잡아 이름표가 밀리지 않게 했다.
- **로딩 장면 하나로 통일** — `index.html`, `GameLoadingScreen.jsx`, `RanchSceneCurtain.jsx`
  - 하늘색→연두색 바탕에 알이 통통 튀는 장면을 세 곳에서 같은 모양으로 쓴다: HTML 스플래시, 화면 JS 대기 화면, 목장 준비 커튼.
  - 세 장면이 이어질 때 애니메이션 박자도 이어받아 알이 다시 나타나거나 튀지 않는다.
  - 목장 준비 커튼은 목장 그림(배경·흙길·대객체)이 다 준비될 때까지 덮는다. 상한은 8초이고, 오래 걸리면 진행 막대가 나타난다.
- 해시가 붙은 `/assets/*` 파일은 Vercel에서 1년 동안 캐시하게 했다(`vercel.json`).

### 3-2. 2단계: 장면 전환 연출 (`8ba0c6a`)

- **원형 커튼** — `src/components/transition/SceneTransitionProvider.jsx`, `SceneCurtain.jsx`
  - 상태는 `idle → covering → covered → revealing → idle`이고, 타이머·애니메이션은 렌더와 무관한 `SceneMachine` 객체 하나가 관리한다.
  - 원이 다 덮인 순간 이동한다. 원을 화면보다 15% 크게 그려, 다 덮인 뒤에도 조금 더 퍼지는 동안 다음 화면이 그려진다.
  - 다음 장면 그림이 준비됐다는 신호(`markReady`)가 오면 걷는다. 기다림이 400ms를 넘으면 장소 이름 아래에 로딩 알이 나타난다.
  - 감시 타이머가 있어 어떤 경우에도 커튼은 정해진 시간 안에 걷힌다.
- **도착 페이드** — `ArrivalVeil.jsx`
  - 자주 오가는 화면(목장↔도감·상점·미션 등)은 새 화면이 이미 그려진 위에서 덮개만 200~240ms 동안 걷는다. 이동 지연은 0ms다.
- **팝업·토스트·튜토리얼 말풍선 등장 연출**, 누른 버튼이 살짝 눌렸다 튀는 탭 팝.
- **모션 줄이기**: 기기 설정을 따른다. 원 대신 같은 색 화면이 짧게 옅어지고 짙어지기만 한다. framer-motion 연출에도 `MotionConfig reducedMotion="user"`로 한 번에 적용했다.
- 첫 주소 `/`부터 튜토리얼 전체를 돌리며 찾은 기존 버그도 함께 고쳤다.
  - "목장으로 돌아가기"를 두 번 빨리 누르면 서식지 단계를 건너뛰던 문제
  - 튜토리얼을 다시 시작해도 확대된 목장 카메라가 그대로 남던 문제
  - 높이 393px 가로 폰에서 튜토리얼 환영 말풍선과 첫 알 안내창의 버튼이 잘리던 문제

### 3-3. 리뷰 반영 (이번 커밋)

2단계 뒤 독립 리뷰에서 확인된 문제와 실측에서 남은 문제를 고쳤다.

| 문제 | 원인 | 수정 |
|---|---|---|
| 커튼이 걷히는 동안 누른 탭이 무시됨. 버튼은 눌린 것처럼 보이는데 아무 일도 없다 | 걷는 동안 커튼은 입력을 통과시키지만, 전환이 끝날 때까지 새 요청을 버렸다 | 걷는 중에 아이가 누르면 걷던 커튼을 바로 끝내고 새 전환을 시작한다 |
| 느린 회선에서 서식지에 처음 들어갈 때 그림이 오기 전에 커튼이 걷힘 | 기다림 상한이 1.2초였다 | 상한 2.2초, 감시 타이머 3.2초. 그동안 장소 이름과 로딩 알이 보인다 |
| 서식지에서 목장으로 처음 돌아올 때 대객체가 잠깐 빈 채로 보임 | 그림 파일은 준비됐지만, 화면의 `<img>`는 처음 그릴 때 따로 decode했다 | 지도 안 대객체 `<img>`의 `decode()`가 끝난 뒤에 준비 신호를 보낸다 |
| 앞 화면의 준비 신호로 커튼이 걷힐 수 있음 | 덮인 동안 주소가 다른 화면으로 또 바뀌는 경우를 구분하지 않았다 | 준비 신호를 보낸 경로와 지금 경로가 같을 때만 걷는다 |
| 미리받기가 한 번 실패하면 그 화면으로 갈 때 흰 화면 | 브라우저가 실패한 `import()`를 기억해 같은 페이지에서는 다시 받지 않는다. 앱에 오류 경계가 없었다 | `ChunkErrorBoundary`를 추가했다. 화면 JS를 못 받으면 로딩 장면을 보이며 한 번 새로고침하고, 30초 안에 또 실패하면 "다시 시도" 버튼을 띄운다 |
| 도감을 훑어 내리면 카드가 빈 채로 오래 보임 | 카드 그림을 화면에 들어온 뒤에야 받기 시작했다. 목록이 안쪽 스크롤 상자에 있어 뷰포트 기준 여백도 효과가 없었다 | 두 단계로 나눴다. 지금 화면에 보이는 카드는 뷰포트 기준으로 바로 받는다. 화면이 자리 잡은 1.2초 뒤부터는 실제로 스크롤되는 상자를 기준으로 한 화면 높이만큼 아래도 미리 받는다 |
| 화면 JS를 기다리는 동안 튜토리얼 카드가 로딩 장면 위로 비칠 수 있음 | 로딩 장면 z-index(80)가 튜토리얼(110)보다 낮았다 | 115로 올렸다. 원형 커튼(120)과 회전 안내(2000)보다는 아래다 |
| 브라우저 탭에서 쓰지 않을 목장 배경을 먼저 받음 | `index.html`의 로그인 판정이 앱의 판정(`AuthContext`)과 달랐다 | 같은 규칙으로 고쳤다. 앱·홈 화면 앱은 localStorage, 브라우저 탭은 sessionStorage만 본다 |
| 밝은 화면에서 목장으로 올 때 한 번 어두워졌다 밝아짐 | 목장 도착 페이드 색이 짙은 초록(#0F1F17)이었다 | 기능 화면 바탕과 같은 아이보리로 바꾸고, 페이드를 불투명도 0.8에서 시작한다 |

`vite:preloadError` 이벤트에서 새로고침하는 방법은 쓰지 않았다. 이 이벤트는 유휴 시간 미리받기가 실패해도 나기 때문에, 아이가 노는 도중에 화면이 갑자기 다시 시작될 수 있다.

## 4. 검증

### 4-1. 측정 방법

- Playwright(Chromium 141)로 폰 가로 852×393(배율 2) 홈 화면 앱을 흉내 냈다.
- 측정용 HTTP/2 프록시를 두었다. 하는 일은 API 가짜 응답, 텍스트 gzip, 회선 흉내(느린 1.6Mbps·150ms, 보통 10Mbps·40ms)다.
  - Playwright의 요청 가로채기를 켜면 HTTP 캐시가 꺼져 두 번째 방문을 잴 수 없어서 프록시를 썼다.
- 같은 시나리오를 네 빌드에 똑같이 돌렸다: 변경 전(`d2f1f64`), 1단계(`e7fa096`), 2단계(`8ba0c6a`), 최종(이번 커밋).
- 화면 상태는 매 프레임(rAF) 기록했다. 스크린캐스트 프레임의 픽셀로 빈 화면과 어두운 화면도 교차 확인했다.
- 최종 열 출처: 전체 측정 1회. 다만 도감 미리받기를 마지막에 고쳐서, 도감 첫 진입(S3) 값은 그 뒤에 다시 잰 값이다(관련 시나리오만 다시 측정).

- "애니메이션을 넣자"에서 바로 시작하지 않고, 프레임 단위로 재서 진짜 원인(회선 경쟁, 미리받기 없음, 큰 그림)을 먼저 찾았다.
